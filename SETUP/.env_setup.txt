These are the ways we can setup environment variables based on how long it needs to be kept.

1. Current terminal only (temporary):
   - Description: Variable exists only for the duration of the current shell session.
   - Example: export API_KEY="abc123"
   - Analysis: Ideal for temporary testing or one-off commands. Does not persist 
     after closing the terminal. No file modification required.

2. Persistent for your user:
   - Description: Variable is available in all future shell sessions for the current user.
   - Example: echo 'export API_KEY="abc123"' >> ~/.zshrc   (for Zsh) or ~/.bashrc (for Bash)
   - Analysis: Survives terminal restarts and reboots for the user. Requires shell restart or 
     sourcing the file to take effect in current session. Best for user-specific settings like default 
     editors or paths.

3. System-wide:
   - Description: Variable is available to all users and system services.
   - Example: echo 'API_KEY="abc123"' | sudo tee -a /etc/environment
   - Analysis: Affects all users on the system. Requires sudo privileges. 
     Variables are loaded at login/pam session start. Not ideal for secrets due to world-readable file.
     Use for system-wide configuration like PATH or JAVA_HOME.

4. Project-specific:
   - Description: Variable is scoped to a specific project, typically loaded by the application.
   - Example: Create a .env file in project root with: API_KEY="abc123"
             Then use a loader (e.g., Python's python-dotenv, Node's dotenv) to load into process.env.
   - Analysis: Keeps project configuration separate and version-control friendly 
     (add .env to .gitignore). Allows different environments (dev/staging/prod) via separate files. 
    Requires application-level loading mechanism. Does not affect the shell environment directly.


It depends on how long you want the variable to exist:

Current terminal only: just run export ... — no file needed.


Persistent for your user: put it in ~/.bashrc (Bash) or ~/.zshrc (Zsh).


System-wide: /etc/environment can be used.


Project-specific: commonly use a .env file, then load it into the environment.
